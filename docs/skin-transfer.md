# Maya 一键发送权重到 Max

蒙皮插件底部“发送权重到 Max”读取 Maya 当前选中的单层蒙皮模型，通过中台现有 Max 客户端导入同机 Max 场景。两个 DCC 必须已连接；Max 未连接时立即记录错误，不调用 Maya、不等待重连，不启动或自动配置 Max。发送只读 Maya，不先限制影响数或截成五位小数。

## 批量写入前关闭权重窗口（2026-11-17）

用户同模型31009顶点实测，Max原生Weight Tool打开时总耗时109.897秒，手动关闭后3.665秒。检查发现本地权重文件导入已有关闭Weight Tool的处理，Maya发送入口遗漏；暂停视口重绘不能替代关闭这类编辑窗口。

Maya发送入口现在对通过预检的模型，在激活/创建目标Skin后、读取影响映射及任何添加/写入之前，分别查询并关闭已打开的Weight Tool和Weight Table。导入后保持关闭，用户需要时可手动重开；预检跳过的模型不进入这段处理。关闭失败时终止该模型，不继续修改权重。普通权重精度、DQ来源规则、最大影响数及逐点/按骨骼批量算法保持原有行为。

使用Skin原生isWeightToolOpen/closeWeightTool及isWeightTableOpen/closeWeightTable，不枚举系统窗口，不更改共享桥接/主窗口。已有本地文件导入入口保持原样。专项测试覆盖逐点路径、已有Skin批量路径、窗口关闭顺序及关闭失败；独立Max场景实际打开窗口并逐点核对权重和DQ。证据见build/skin-transfer-weight-window-tests.log和build/skin-transfer-weight-window-native-run.log。用户日志中的约30倍差异属于用户场景观测，不作为其他场景的提速承诺。

最终37项传输专项、邻近Max权重专项通过；隔离Max2020/Python2.7真实窗口测试通过，宿主退出0，覆盖4顶点逐点路径及1024顶点按骨骼批量路径，全部顶点权重和DQ均读回通过。Weight Tool在两种路径均先打开再由导入关闭，Weight Table另在小模型验证。约3万顶点的直接批处理测试出现原生EXCEPTION_ACCESS_VIOLATION，保留的未修改基线在相同样例同样失败，因此未声称该规模原生测速通过；失败也不能据此认定用户交互场景必然有同样问题。证据build/skin-transfer-weight-window-baseline-native-run.log。曾尝试rollout定时入口，但该批处理消息循环没有生成结果，未采用该验证结论。

此修改先同步开发源码，未重新打包dist。已运行的打包版继续使用其自身动作文件，需要更新打包版后生效；仅重载旧打包版动作不会读取开发目录的新源码。

## 用户确认的第一版规则

- 使用 Maya transform 短名寻找 Max 唯一同名对象；模型名和骨骼名只将 FBXASC032 解码为空格，不移除 namespace、不模糊匹配。Maya 解码后同名、Max 同名不唯一均跳过报告。
- 核对 Max 现有 Skin 实际处理的顶点数；无 Skin 时使用目标网格顶点数。相同顶点数仍依赖两边已有一致的顶点编号，骨骼初始姿态由制作流程保证。不做空间匹配，不发送模型、骨架或绑定矩阵。
- 仅检查实际有正权重的骨骼。骨骼在 Max 场景缺失或重名时，导入前跳过整个模型并报告；场景中存在但目标 Skin 尚未包含时，代码自动添加到 Skin，再建立骨骼 ID 对应。没有 Skin 则创建；多个 Skin 暂不猜测目标。
- 读取 Maya skinningMethod，发送完整权重及每顶点 blendWeights。源为线性（0）时，Max 只导入普通权重，不调用 DQ 写入接口，保持目标现有 DQ；源为双四元数（1）或混合（2）时才覆盖每顶点 DQ。仅根据 Maya 来源判断，不读取或切换 Max enableDQ 开关。
- 所有顶点的完整权重都会发送。导入后把 Skin.bone_limit 设置为卡片 max_inf_sbox 的值，不固定成4。写入阶段临时容纳源影响数，避免已有较小上限干扰，最后再设置界面值；发送端不会按此值提前裁剪权重。
- 全零、负值或非有限数的源权重，以及非有限或超出0～1的DQ数据，跳过整个模型；避免形成一部分新权重、一部分旧权重的混合结果。错误在中台日志显示，其他合法模型继续处理。

## 数据和线程

Maya 主线程动作 skin_weights_export_max 使用既有 _Mesh 的批量读取与 struct 编码，附加模型/骨骼名称、skinning_method 和 getBlendWeights。NumPy 在中台后台线程把稠密 float64 快照转换为全顶点 CSR：uint32[V+1] offsets、uint32[N] influence列号、float64[N]非零权重，以及float64[V] DQ。文件位于本机 qz-skin-transfer-* 临时目录，JSON只传尺寸和名称。保留 float64 传输精度，不在此流程量化；Max 最终数值精度取决于其原生 Skin 存储。uint32交换格式会明确拒绝单模型非零项超过4294967295。

Max 动作 skin_weights_import_max 经既有主线程 worker 执行 pymxs；socket线程不接触Max API。完成模型/骨骼/文件匹配后添加缺失Skin影响；Max2020满足数据条件时按骨骼批量覆盖，需要时先批量初始化，其他情况使用 ReplaceVertexWeights 逐顶点覆盖。逐顶点和批量两条路径都按源 skinning_method 决定是否写入每顶点DQ；禁用重绘在 finally 中恢复，最后选择成功导入的模型。

插件仍沿用 create_widget(client, log, parent) 工厂签名。MainWindow 对声明 set_dcc_clients() 的插件注入同一份已存在的客户端字典；不创建额外Max客户端、不猜测端口、不影响Maya/Max独立连接。发送按钮位于检测/修改分组下方的独立QGroupBox，沿用公共QSS；后台任务期间禁用卡片输入，结果在UI线程写中文日志，不改变原Maya最大影响检测显示。日志仅显示操作结果、失败原因及总耗时，不显示各阶段调试计时；详细计时保留在内部响应中。

Skin识别使用`rt.classOf(modifier) == rt.Skin`，不依赖当前Max中不可用的`rt.classID`。测试替身不提供classID，混合修改器堆栈也需正确找到现有Skin。

## 连接等待与错误边界

Max原生异常处理（2026-11-06）：bootstrap在ExecuteFile失败后停用timer，并写本进程
专用临时失败标记。socket线程只检查文件，不调用pymxs；发现失败后结束正在等待的
请求，附上最后一个Skin API阶段，卡片恢复可操作。尚未开始的超时/失效任务不再执行，
重新启动桥接时也会释放旧队列。故障后的已有Skin可能部分更新，不自动重试。
正常长任务运行时，socket线程可回复busy心跳，避免心跳排在导入后面造成误断连。

中台关窗先shutdown/关闭客户端当前socket，唤醒最长305秒的recv，再等待线程池收尾。
这仅停止本地等待，不会强行停止Max里已开始的写入。版本信息读取后台心跳缓存，
UI线程不再额外同步ping。新核心必须重启Max加载；仅重载动作库不能更新server模块，
start_max会检测旧核心并明确提示。中台也需重启加载新的退出处理。

DccClient.call() 新增可选 connect_timeout 与 execution_timeout，后者作为请求顶层字段传给Max桥。发送使用连接上限1秒、执行等待300秒、客户端接收上限305秒；其他动作省略这些参数时保持原行为。Max桥验证执行时长在(0,3600]，默认仍10秒。未连接的情况在发请求前立即返回，长执行等待只用于已连接任务。

Max 桥新增 SUPPORTS_EXECUTION_TIMEOUT 标记。旧桥仅重载动作仍可能保留旧server模块，新导入动作会在写入前提示更新桥接，避免旧固定10秒误报后继续导入。需要重启Max或重新启动新版桥接，随后重载动作库。Maya需重载动作库；中台需重启开发版以加载新按钮及客户端注入。超时不能视为已取消写入，不自动重试。

若新建Skin过程中失败，移除本次新建Skin；已有Skin导入中途失败时，明确报告已处理顶点数及可能部分更新，不伪装成功。本版没有为Max已有Skin增加全量备份、Undo或写后逐项复查。选择不匹配、缺骨骼及坏文件在写权重前拒绝。

## 新建Skin与缺失顶点影响的批量初始化（2026-11-06后续）

用户指出创建Skin/添加骨骼本身不应阻止批量导入。本轮已去除“新建Skin或补骨骼必走
逐点写入”的限制；1024顶点是性能切换阈值，100万条是内存保护，不是Skin原理要求。
Max2020版本门槛保留，因为其他版本的批量接口签名尚未原生验证。

直接放开限制的原生实验虽然约4秒，但全量读回出现旧权重残留，另有缺影响场景触发
原生访问异常，不能采用。按骨骼逐批选择顶点并SetWeight建立关系可以通过校验，但
新建Skin约16.8秒，初始化成本抵消收益，也未采用。

正式方案在需要时统一选择全部顶点，先以Skin中的第一根骨骼SetWeight=1，再以第二根
SetWeight=0.5（仅一根时只需第一次），用两次原生命令建立稳定基底。随后临时暂停
逐点归一化，按骨骼批量补入缺失的正影响，再写完整源权重，包括明确清零旧影响，
最后写DQ并恢复原归一化状态。临时基底数值不作为最终结果；源数据仍保持完整精度。
初始化函数在finally恢复自己的骨骼/顶点选择；整个动作仍沿用原有面板激活及最终
选择模型的行为，因此不承诺动作前后Skin面板当前骨骼完全不变。

新建Skin/补入骨骼先只检查源数值，再直接初始化，避免扫描即将被覆盖的旧影响。
已有Skin先读影响ID、归一化标记和IsVertexModified；缺任何源影响或存在未修改的封套
控制顶点时执行初始化，否则保持原快速覆盖。没有现有影响条目、超容量、源非单位和
或单值大于1等仍保留原逐点覆盖；初始化及批量接口失败时不自动重试。新建Skin失败
仍清理该Skin，已有Skin失败仍报告可能部分更新。用户日志继续只显示结果与总耗时。

最终正式代码经真实rollout验证49729顶点、131骨骼：删除Skin重建两次6.212/6.216秒，

## 源蒙皮方式控制 DQ（2026-11-06）

Maya 每次导出读取 skinCluster.skinningMethod，0=线性，1=双四元数，2=混合。三种方式都采集普通权重和 blendWeights，数据数组不变。中台将该字段逐模型传递；来源未提供有效方式时跳过并提示重载动作库，不依据 DQ 数值推断来源模式。Maya 原生枚举说明：[Autodesk skinCluster](https://help.autodesk.com/cloudhelp/2024/ENU/Maya-Tech-Docs/CommandsPython/skinCluster.html)。

Max 只依据来源方式决定每顶点 DQ 是否覆盖，源线性时连 DQ setter 都不调用，不清零、不转换、不读取/切换 Max 模式；新建 Skin 则保留其初始 DQ。普通权重、缺骨骼检查、骨骼添加、最大影响数和批量加速照常执行。同一批不同模型独立判断。结果报告携带 skinning_method 和 dq_imported；用户日志明确显示“已同步 DQ”或“源为线性蒙皮，保留 Max 原有 DQ”。
